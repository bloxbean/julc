# ADR-041: Integer Case dispatch for sealed-interface switches (O5) and the Unit Case decision (O6)

**Date:** 2026-09-13
**Status:** Implemented and locally validated on `feat/112-integer-case-dispatch`; independent review pending
**Issues:** [#112](https://github.com/bloxbean/julc/issues/112) (O5), [#113](https://github.com/bloxbean/julc/issues/113) (O6)
**Governing decisions:** ADR-032 O5/O6 (research classification), ADR-036/ADR-038 (the dispatch site), ADR-039 (decompiler recovery), ADR-015 (strict typed boundaries)

## Context and current behavior

Every `switch` on a sealed interface lowers to a `DataMatch`. `UplcGenerator.generateDataMatch`
decodes the scrutinee once (`UnConstrData`, then the ADR-038 native pair Case or the legacy
`FstPair`/`SndPair` lets) and dispatches on the native integer tag with an equality chain:

```text
if equalsInteger tag 0 then B0
else if equalsInteger tag 1 then B1
...
else error
```

Under `PV11_SAFE` the O2 rule already turns each `if` into `Case Bool`, so the chain costs one
`EqualsInteger` application plus one `Case` per constructor tried. The cost therefore grows with
the position of the selected constructor, and the last constructor of an n-way switch pays n
comparisons. `PatternMatchDesugarer.buildDataMatch` emits exactly one branch per constructor in
tag order and fills missing arms with the `default` body or an `Error`, so the tag domain is
dense: branch `i` is the branch for tag `i`.

Plutus V3 protocol version 11 adds `Case` on builtin integers: `case i [b0 .. bn-1]` selects
branch `i` in one machine step and fails for any other value. ADR-032 classified O5 as research
and issue #100 deferred it because a raw Case changes the failure text on an invalid tag and
cannot express a Java `int` switch default. Issue #112 asked for a source-semantics decision.

O6 asked whether statement sequencing should lower through `Case Unit`. ADR-032 described the
candidate as replacing `ChooseUnit` sequencing; JuLC never emits `ChooseUnit`. Sequencing lowers
as `Let("_", e, rest)`, which becomes the application `[(λ_. rest) e]`.

## Goals and non-goals

Goals:

- Lower compiler-generated sealed dispatch with two or more constructors to one integer `Case`
  under the exact PV11 target and the safe profile, keeping every success result, trace, and
  failure point identical and never increasing the budget on any path.
- Define the failure contract for a constructor tag outside `0..n-1` precisely, and make the
  VMs honor it for the full integer domain.
- Keep ADR-039 decompiler recovery working on the new shape.
- Decide O6 on measurement.

Non-goals:

- Java `int` switches. JuLC only supports `switch` on sealed interfaces; there is no
  integer-scrutinee switch to lower, and a `default` arm on integers cannot be expressed by
  `Case`.
- `instanceof` chains. `PirGenerator.generateInstanceOf` emits its own `EqualsInteger` on the
  tag per test and never builds a `DataMatch`; they stay as written. (The desugarer's
  `buildFromInstanceOfChain` helper is unused by the generator; if it were ever wired in, it
  fills every missing variant, so the dense-domain invariant would still hold.)
- Byte changes under `NONE` or `BASELINE`.
- Any change to what a strict typed boundary accepts.

## Invariants and proof

1. **Dense tag domain.** `buildDataMatch` iterates `sumType.constructors()` in declaration
   order and adds one `MatchBranch` per constructor, so `branches.get(i)` is the branch for tag
   `i` and `branches.size()` equals the constructor count. The legacy chain relied on exactly
   this by comparing the tag with the branch index. `Case` uses the same index.
2. **Success set unchanged.** For a tag in `0..n-1`, the chain reaches branch `i` after `i+1`
   comparisons that have no effects; `Case` reaches the same branch body, generated by the
   same `buildBranchFieldExtraction`, with the same field decoding in the same order.
3. **Branch laziness.** UPLC `Case` evaluates only the selected branch. The chain's branches
   were delayed (`Delay`/`Force`, or `Case Bool` under O2), so unselected branches were never
   evaluated before either.
4. **Scrutinee strictness.** The tag binder is already bound by the enclosing `PairMatch` or
   `Let`, so `Case` on the variable adds no evaluation and reorders nothing.
5. **Failure point.** For a tag outside `0..n-1`, the chain evaluated n comparisons and then
   the terminal `Error`; `Case` fails at selection. Both fail after the scrutinee decode and
   before any branch effect, with no traces emitted in between.
6. **Representation.** The scrutinee is the native integer tag of `UnConstrData`, bound by the
   ADR-038 pair Case branch or by the legacy `FstPair` let; nothing Data-encoded is cased on.
7. **Determinism.** The lowering is a pure function of the `DataMatch` and the gate.

## Failure contract decision

ADR-032 invariant 3 preserves failure semantics "unless a separately accepted
language-semantic ADR changes the contract". This ADR is that decision, and it is deliberately
narrow:

> Compiler-generated sealed dispatch with n ≥ 2 constructors selects branch `i` for tag `i`
> and fails at selection for every other tag, including negative values and values beyond the
> machine integer range. The failure carries no trace and runs no branch. Off-chain, the Java
> and Truffle VMs report `Case: tag T out of range for N branches`; Scalus reports
> `Case index T out of bounds for N branches`. The legacy chain reported
> `Error term encountered` (Scalus: `Error evaluated`).

On-chain a failure is a failure; the ledger observes no text. The change is therefore
observable only in off-chain failure text and in the budget consumed on the failing path,
which is smaller.

**Reachability.** Every validator fixture in `O5IntegerCaseLoweringTest` shows *identical*
budgets before and after the rule for out-of-range tags (`constr(99)`, `constr(2^40)`, an
inner field with tag 3, and a tag one past the last constructor). Under ADR-015 the strict
typed boundary validates constructor tags of datum and redeemer roots and nested typed fields
before user logic runs, so those inputs never reach the dispatch. Ledger-provided sum types
(`ScriptInfo`, `OutputDatum`, `Credential`, and so on) are well-formed by construction. The new
failure text is reachable through three paths, none of which is a validator entrypoint:

- `JulcCompiler.compileMethod`, and therefore the testkit's `JulcEval` and `MethodEvaluator`,
  which decode sealed parameters without the strict boundary. A testkit call such as
  `eval.call("run", PlutusData.constr(99))` on a three-variant switch now fails with
  `Case: tag 99 out of range for 3 branches` instead of `Error term encountered`. This is
  the one compiled-Java path where the change is observable, and it is pinned by
  `O5IntegerCaseLoweringTest.compileMethodPathReachesDispatch…` on all three VMs and by the
  testkit's `SealedDispatchFailureTextTest`.
- Direct PIR consumers (`compilePirToProgram` with a hand-built `DataMatch`, as in
  `SwitchPairCasePirTest`).
- Sealed values a validator obtains without a typed boundary: an inline or reference-input
  datum read as `PlutusData` and cast to a sealed type, a `JulcList`/`JulcMap` element decoded
  from raw Data, or an `@OnchainLibrary` helper that converts raw Data to a sealed type by hand.

On such a value with a tag outside `0..n-1`, both the old chain and the new Case fail at
dispatch; only the text differs.

**VM hardening.** Both the Java CEK machine and the Truffle `CaseNode` narrowed an integer
scrutinee with `intValueExact()` before range-checking it, so a tag beyond the `int` range
raised an `ArithmeticException` that surfaced as a generic failure with no source attribution.
Constructor tags are unbounded non-negative integers, so with O5 that path is reachable from
program input. Both VMs now compare the full value against the branch count first and fail
with the standard out-of-range machine error; the conformance fixtures `integer-01..04` and
the new gating tests pin `-1`, `n`, `2^40`, `2^64` and `-2^64` on Java, Truffle and Scalus.

## Decision

- Add a generator-local PIR node `PirTerm.IntegerCase(scrutinee, branches)` (at least two
  branches, no binders). `generateDataMatch` produces it instead of the equality chain when
  `branches.size() >= 2` and the shared O3/O4/O5 gate holds: exact `PLUTUS_V3_PV11` target,
  `pv11SafeRulesEnabled()`, and `CASE_ON_BUILTIN_CONSTANTS`. It lowers to
  `Term.Case(tag, [B0 .. Bn-1])`. Single-constructor matches keep their unchanged
  field-extraction body. The rule applies inside both the ADR-038 pair Case and the legacy
  `__match_pair` expansion, since the dispatch is orthogonal to the binder shape.
- Rule provenance: `pv11.o5.case-integer` in the optimization report.
- `NONE` and `BASELINE` keep their historical bytes; `PV11_SAFE` and `PV11_COSTED` change bytes
  and hashes for every program containing a sealed switch with two or more constructors.
- Failure-equivalence tests accept exactly the substitution above, within one VM family's
  wording, and nothing else (`CaseFailureEquivalence`). The validator fixtures never trigger
  it, because the strict boundary rejects invalid tags first; the `compileMethod`-path test
  and the raw-term test pin that the Case text names the exact tag and constructor count on
  Java, Truffle and Scalus, and the direct-PIR suites exercise the substitution itself.
- Decompiler: `DataMatchRecognizer.matchConstructorDispatch` recognizes a `Case` on the tag
  binder (de Bruijn index 2 under the fields binder) with two or more branches as constructor
  dispatch, one `TagBranch` per branch, with `Builtins.error()` as the rendered residual.
  ADR-039 recovery, scoped-name resolution, and the `if (tag == N)` reconstruction are
  preserved for PV11_SAFE output.

### O6 decision

O6 is **rejected** for this milestone. JuLC emits no `ChooseUnit`; the only sequencing shape
is `[(λ_. rest) e]`, and rewriting it to `case e [rest]` is correct only when `e` is proven to
evaluate to unit. A `Case` on an integer or boolean statement value would select a branch by
that value. The compiler has no typed Unit statement surface, and the discarded values in
shipped artifacts are dominated by `error` terms (which never return) and trace applications.
The per-site saving is one lambda plus one application, a few bytes and roughly two CEK steps.
The census that grounds this is recorded in the evidence document; if a typed Unit statement
surface is ever added for another reason, O6 can be revisited as a bounded rule on that node.

## Alternatives rejected

- **Guarded Case** `case (lessThanInteger tag n) [error, case tag [B0..]]` to keep the exact
  `Error` failure text. It adds a constant `LessThanInteger` application, a `Case Bool` and a
  variable lookup to *every* path, so the first-constructor path costs two machine steps more
  than the chain it replaces. It can never meet the non-increasing-on-every-path bar that
  ADR-036 and ADR-038 set, and it protects only an off-chain string on inputs the strict
  boundary already rejects.
- **Only for three or more constructors.** The guarded form has the same first-branch penalty
  at any n; the unguarded form wins at every n ≥ 2, including the two-constructor case that
  dominates real validators.
- **A new explicit "bounded integer match" source API**, as #112 originally framed it. There
  is no user-level integer switch to give it to, and sealed dispatch already is a bounded,
  no-default match with a dense domain.
- **Rewriting `instanceof` chains.** They are user-written conditionals with their own
  `EqualsInteger` per test and no dense-domain guarantee.
- **O6 as an untyped `[(λ_. rest) e]` rewrite.** Unsound for non-unit statement values.

## Compatibility and risks

- **Script bytes and hashes.** Recompiling any validator with a sealed switch of two or more
  constructors under `PV11_SAFE` or `PV11_COSTED` changes its bytes and hash. `NONE` and
  `BASELINE` are byte-identical to the captured goldens. Deployed scripts and ledger Data
  encodings are unchanged. The Blaster verification suite compiles at `baseline` and its
  artifact lock is unaffected.
- **Direct PIR consumers** see the new failure text on invalid tags, as documented above.
- **External HIR consumers** of the decompiler see no new node; `DataMatch` is reused.
- **Risk: branch-order drift.** If `buildDataMatch` ever stopped emitting one branch per
  constructor in tag order, `Case` would misdispatch silently where the chain would have
  errored. `O5IntegerCaseLoweringTest` pins the branch count per site and the observational
  equivalence of every branch against the pre-change goldens; the desugarer invariant is the
  load-bearing assumption and is documented at the producer.

## Verification

- `O5IntegerCaseLoweringTest` (tag `pair-case-backends`, run by `pairCaseTest`): historical
  bytes at `NONE`/`BASELINE`, smaller bytes and changed hash at safe levels, deterministic
  bytes, rule provenance, observational equivalence on Java, Truffle and Scalus for every
  scenario including first/last branch, `default` arm, nested inner dispatch, wrong field
  types, extra and missing fields, non-constructor input, and tags `n`, `99`, `2^40`;
  budgets never increase on any path; the dispatch shape is one `Case` on the tag binder per
  switch and the program loses exactly one `EqualsInteger` per constructor per dispatch site;
  every arm traces and only the selected arm's trace appears, including a failing arm; the
  `compileMethod` path with five distinct-result arms pins each branch and the exact Case
  failure text (tag and count) for tags `n`, `99`, `2^40` against the legacy text at
  `BASELINE`; raw `case` terms with traced branches fail at selection for `-1`, `n`, `2^40`,
  `±2^64` with no trace on all three VMs; producer guards reject fewer than two branches and
  non-safe profiles.
- `SwitchPairCasePirTest`, `SwitchPairCaseLoweringTest`, `PairCaseLoweringTest`: unchanged
  expectations except the failure-text contract via `CaseFailureEquivalence`; a new two-branch
  legacy-`__match_pair` case asserts O5 is recorded and O4 is not.
- Testkit `SealedDispatchFailureTextTest`: `JulcEval` observes the Case text for tags `n`,
  `99` and `2^40` on a three-variant switch.
- `ProtocolGatingTest` and `ProtocolGatingParityTest`: full-domain integer Case failures with
  exact text and equal budgets on both VMs.
- Decompiler: `ConstructorDispatchTest.recognizesIntegerCaseDispatchOnTheTagBinderOnly`
  covers both producer shapes, tag order, the `Error` residual, rendering, round-trip
  evaluation including an out-of-range tag, and the negatives (fields binder, outer binder,
  single branch, lambda branches); `SwitchPairCaseRecognitionTest` recovers compiled
  PV11_SAFE output as a `DataMatch`.
- Node evidence: `switchPairCaseOnChainTest` against the running Yaci DevKit compares Java,
  the backend endpoint, and direct Haskell `cardano-cli` budgets for the new dispatch. Results
  are recorded in `adr/evidence/041-integer-case-dispatch.md`.
- Suites: compiler, `pairCaseTest`, VM Java (999 PV11 conformance cases), Truffle, decompiler,
  stdlib, testkit, examples; docs build; Blaster `prepare-artifacts.sh` lock check.

## Open questions

- Whether the `PV11_SAFE` rule set should be frozen after the P4 wave, so that later rules
  land only in a new opt-in profile (tracked on #121).
- O2's gate omits the exact-target clause that O3/O4/O5 share; harmless today because
  `CASE_ON_BUILTIN_CONSTANTS` already implies PV11, but worth unifying in a follow-up.
