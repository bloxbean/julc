## 2. Tests changed

The rule (the coordinator's brief): a test about the JavaParser frontend, the I1 reference or the reference tooling selects
`JAVAPARSER` explicitly; a test whose subject is not the frontend runs on the new default, and where javac answers
otherwise by a decision of the ADR its assertion reads javac's answer; no assertion is weakened.

**Mechanical pinning.** `setFrontend` sets a field and a later call wins, so prefixing a chain with
`setFrontend(JAVAPARSER)` changes nothing where the chain selects a frontend itself, and keeps the frontend the code had
before elsewhere. The script (`<M0>/work/m5b/tools/pin.py`) did that for `new CompilerOptions()`, `new LedgerTypeProvider()`
and one-argument `new JulcCompiler(x)`, outside string literals, in:

- every test source of `julc-difftest` (the I1, baseline, types, encodings, evaluations, recheck, contract and gate-timing
  tooling; `Adr068Ledger.options` is the reference's options for every gate): 16 files;
- every `julc-compiler` test source that names a frontend, the gate or `DialectGate`, or lives in `frontend/javac`
  (`<M0>/work/m5b/aware-compiler.txt`, 76 files; 40 had a default site, 182 sites,
  `<M0>/work/m5b/pinned-compiler.txt`). Before M5 each of those defaults meant JavaParser, the reference; these files test
  javac with an explicit `JAVAC` already;
- the corpus recorder's probes.

That is no change of behaviour: each pinned site compiles as it did at `4d403623`. Sites the script could not see
(`new JulcCompiler()`, `JulcEval`, `ValidatorTest`) were read one by one; three were references and are pinned below.

## 3. Diagnostics

`JULC0087`'s message is unchanged (`<operation> compares <type>, whose equality on the JVM compares an array by identity`;
for `byte[].equals`: `Object.equals compares byte[], whose equality on the JVM compares an array by identity`). Its fix,
which every `JULC0087` carries as its suggestion, is now:

> Compare the bytes: Builtins.equalsByteString(a, b) for byte[], which keeps the script the JavaParser frontend made for
> a.equals(b) (ByteStringLib.equals(a, b) is equivalent, a few bytes larger), and Builtins.equalsByteString(a.value(),
> b.value()) on the component accessors of a @NewType byte wrapper. Where the type cannot be read, compare at the value's
> own declared type. Until ADR-068 M6 the JavaParser frontend, which compares the bytes on-chain but by identity on the
> JVM, stays selectable: julc build --frontend javaparser, julc { frontend = 'javaparser' } in Gradle, or
> CompilerOptions.setFrontend(CompilerFrontend.JAVAPARSER).

**Why the builtin (the coordinator's decision).** The examples agent found that `ByteStringLib.equals(a, b)`, which D6
named, changes 16 of 23 external validators by +2 to +30 bytes against `byte[].equals`: the library method is let-bound as
an alias of the builtin and called through a variable. `Builtins.equalsByteString(a, b)` keeps the builtin inline, as the
JavaParser frontend lowered `a.equals(b)`, so the bytes and hashes stay. `ByteEqualsRemedyTest` pins byte identity for a
method and a loop. D6 now says so (r17 clarification); the inlining of such aliases is a follow-up row.

Other texts:

- `JULC0086`'s fix: "Use a.equals(b), or Builtins.equalsByteString(a, b) for bytes (ByteStringLib.equals(a, b) is
  equivalent)."
- `JULC0084`'s summary no longer says "the default frontend is unaffected"; its fix: "Write the construct another way within
  the subset, or report it. Until ADR-068 M6 the JavaParser frontend may compile it: julc build --frontend javaparser,
  julc { frontend = 'javaparser' } in Gradle, or CompilerOptions.setFrontend(CompilerFrontend.JAVAPARSER). If that
  frontend rejects it too, it is outside the subset." No corpus program reaches `JULC0084`.
- `JULC0085`'s and `JULC0089`'s summaries say both the javac frontend and the gate emit them.
- **Where the way back is named, and where not.** Only `JULC0087` and `JULC0084` name the JavaParser frontend. For
  `JULC0087` the JavaParser frontend's script compares the bytes, as the user meant (only its JVM tests differ); for
  `JULC0084` it is the only remedy. The other D15 codes (`JULC0078`, `JULC0086`, `JULC0012`, `JULC0123` to `JULC0129`,
  `JULC0014`) are Policy rejections of shapes the JavaParser frontend reads otherwise than Java, so a hint to go back would
  point users at a known divergence; their fixes name the Java remedy, and the release notes say how to opt back in general.
  Each D15 code's message and fix was read: each names the construct and a remedy (`diagnostics.json`).

**Hosts that printed only the words.** The javac frontend raises most rejections as a `CompilerException` of one
diagnostic, whose `getMessage()` is the diagnostic's words alone. The annotation processor printed
`"Plutus compilation error: " + e.getMessage()` and the Gradle plugin's `compileJulc` let the exception through, so on the
new default a `byte[].equals` build failed with "Object.equals compares byte[], whose equality on the JVM compares an array
by identity" and no code, position or fix. `CompilerException.describe()` (new, public) gives each diagnostic with its code,
position and fix; the processor prints it and `compileJulc` wraps it in its `GradleException`. The CLI already printed the
diagnostics (`DiagnosticFormatter`). The testkit still shows the words alone (gap 11).

## 5. The `byte[].equals` codemod

A codemod exists: `DialectCodemod` (`julc-compiler/src/test/.../frontend/javac/DialectCodemod.java`, M1b, test tooling, not
shipped; Gradle tasks `dialectCodemod` and kin). It is driven by a javac gate report and rewrites only what **javac**
rejects, by javac key (`cant.resolve`, `operator.cant.be.applied`, `prob.found.req`, `doesnt.exist`,
`non-static.cant.be.ref`): the dialect of D6. `byte[].equals` is valid Java, so javac never reports it, and the codemod has
no rule for it. Not extended (the brief: only if one exists, and the coordinator's later note: the external examples are
migrated by hand on their own branch). What one would need: a rule keyed on `JULC0087` (from the javac frontend's subset
diagnostics, not the gate report), rewriting `a.equals(b)` at a `byte[]` receiver to `Builtins.equalsByteString(a, b)`
with the import, and `!a.equals(b)` to `!Builtins.equalsByteString(a, b)`; records and containers holding `byte[]` need a
person.

## 6. H1 and H3

**H1.** The reasons of `8470b042` (now `JULC0087`, two empty containers, r17) and `1a9eb48f` (`JULC0014`, a Diagnostic change)
in `lowering-accepted-differences.tsv` are rewritten; key and class unchanged, so the I1 tool parses them as before (I1
below). Two sibling rows were checked and are current (`74cea76b` is still `JULC0078` for a `Tuple2`; `23f7342e` and
`94fad4bc` are uncoded on javac too).

**H3.** `NewTypeVariantConsumersTest` compiled the shape (`sealed interface W permits V {}` with `@NewType record V(BigInteger
value)`, and with `static final class V`) on javac through every consumer that does not `new`, `instanceof` or `case` the
variant: a parameter, a sum passed through, a record component, a datum (`compile` and `compileContract`, whose schema a
blueprint is made from), and `JavaLibraryProvider`'s exports. **All of them compiled** (a bypass). The fix:
`RecordDeclarations.requirePlainVariants`, run after lowering in `JavacCompilation.validator` and `method` and after lowering
in `JavacLibraryExports`, rejects with `JULC0127` any sealed interface the program's read units declare whose permitted class
is a class or a `@NewType` record, at the variant's declaration. Running after lowering keeps every use-site rejection where
it was (the corpus's three conflict rows are use sites), so it reaches only programs that compiled before. The test now
passes for every consumer and both variant kinds, with the default and with explicit `JAVAC`. Not covered: `JavacCompilation.subset`
(the tools' check without compiling) reports pre-lowering rules only, so the playground's check does not show it until a
compile (gap 7); a nested class in a library unit fails earlier with an uncoded `IllegalArgumentException` ("Only
@OnchainLibrary sources can be exported"), fail-closed but not a diagnostic (gap 8).

## 8. Gaps and decisions for the maintainer

1. **D15's "modes on the default frontend".** D15 says a gate rule follows the gate's mode "on the default frontend". The
   code ties the gate to `frontend == JAVAPARSER`, so after the flip the modes apply on the JavaParser frontend only and
   the default (javac) has no gate. The docs say so. The ADR text could say "on the JavaParser frontend" at M6's revision.
2. **The corpus recorder skips javac.** `JulcCompiler.recordCorpus` records string entry points only on `JAVAPARSER`
   ("the corpus is the reference's inputs"), while the path entry points and `JavaLibraryProvider` record on every frontend.
   With javac the default, a new head recording from the test runs would hold almost nothing but those. Decide before the
   next recording: record every frontend (the I1 tool compiles both itself), or keep the rule and record with a property.
   Not changed here: it is gate tooling, and no gate here records.
3. **Dialect tests.** The follow-ups say "delete the dialect tests at M5"; `DialectGate`'s row says "at M6". The tests are
   kept and pinned to JavaParser (the conservative reading, no coverage lost); they go with the frontend at M6.
4. **The verbose log on javac** has no stage lines (parsing, subset, PIR, libraries, `@Param`); it logs the target, version,
   level and now the completion with the size. A follow-up if users rely on the stages.
5. **`JULC0002`'s fix on javac** shows a placeholder (`var x = ...`) where the reference named the variable. A follow-up.
6. **Internals docs** describe the JavaParser pipeline in depth; only a note was added. They are M6's rewrite.
7. **H3 in the tools' check** (`subset`, the playground's `/api/check`): not reported before a compile.
8. **A nested class in a library unit** (Elci's provider) fails with an uncoded `IllegalArgumentException`.
9. **The I1 freeze is not redone here.** No table is re-frozen; I1 reads 0 moved rows (above), so the H3 rule moved no
   corpus row.
10. **Release notes' numbers** (24,167 cases, 14,405 identical, 396 bytes rows, 1,075 policy rejections, the external split)
    are I1's at `4d403623`'s tables; the coordinator's cost and size report may restate them.
11. **The testkit's exception message.** `JulcEval`, `ValidatorTest` and `MethodEvaluator` let the javac frontend's
    `CompilerException` through; its message holds the words, and the code and fix are in `diagnostics()`. A JUnit report
    shows the words only. Printing `describe()` there would change what tests that catch the exception read; left for a
    decision.
12. **`CompilerException`'s message itself** could carry the code and fix for every host, but tests and the I1 tool read
    messages, so it was not changed here.
13. **JRL** is removed (section 9), so it no longer blocks M6.

## 9. JRL removed (the maintainer's decision, 2026-11-04)

The maintainer decided to remove JRL support entirely, now, including from the playground. That replaces `3a6673e4`,
which had pinned JRL's generated Java to the JavaParser frontend (its transpiler wrote `==` between references, which
javac's frontend rejects), and it removes that blocker for M6. JRL was never published to Maven.
