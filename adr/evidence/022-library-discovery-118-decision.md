# #22 library discovery cleanup and #118 decision gate

Base: merged `main` at `3d0e89a9` (PR #123).
Branch: `fix/22-library-discovery-118-decision`.

## Scope and invariants

The initial removal of all but Builtins was incorrect: explicit-library-list
entry points do not scan, and registry-only methods still need FQCN import
resolution. Independent Claude review identified this blocking regression; six
new probes reproduced it before the fix. The previous green build did not cover
explicit empty source lists combined with registry-only methods.

The corrected implementation removes the compiler-owned list entirely. Additive
`StdlibLookup.registeredClassNames()` metadata supplies importable names from
actual registrations, including Builtins, while source-library names continue
to come from parsed compilation units. StdlibRegistry derives names from its
registration table; composite and NewType lookups preserve metadata. See
[ADR-035](../035-lookup-owned-import-names.md) for ownership and compatibility.
Custom lookup decorators with FQCN registrations should propagate this metadata;
the default empty set preserves interface implementability, not automatic
introspection of private registries.

Source scanning, classloader selection, import precedence, lookup/evaluation
order, target legality and ledger encodings are unchanged. No new modular
exponentiation lowering is introduced.

## #118 decision: no additional implementation required

`MathLib.expMod(base, exponent, modulus)` already delegates to
`Builtins.expModInteger`. No distinct supported source contract has been
introduced that needs another recognition rule. Therefore the issue's decision
gate selects no additional implementation. No new O12 rule is enabled at any
optimization level.

Ordinary `MathLib.pow(base, exponent) % modulus` is not equivalent:

- `(2 ^ -1) % 5` returns 1 under the existing MathLib source contract; explicit
  modular exponentiation returns the inverse, 3.
- `(2 ^ -1) % 4` returns 1; explicit modular exponentiation fails because no
  modular inverse exists.
- Modulus failure behavior belongs to the original operation and must not be
  replaced by a different builtin's failure contract.

The existing [O12 research evidence](032-cost-use-rewrite-deferrals.md#o12--ordinary-powmod-is-not-expmodinteger)
continues to apply. A new source abstraction would need a new explicit decision
and full boundary/strictness/target evidence. Tests here protect the rejection,
not enable a new semantic transformation. #118 can close as no additional
implementation required when this decision is accepted.

`ExpModDecisionGateTest` compares BASELINE with PV11_SAFE and PV11_COSTED on

preserve results, exact failure messages and traces. Independent expected-value
assertions distinguish the source contracts, and structural checks ensure only

## Review correction and remaining scope

The original self-review incorrectly generalized source-library discovery to
registry-only methods on explicit-list overloads. It also generalized the
simple-name support of typed overrides to exact-key table lookups. Testing
Builtins with an explicit list did not exercise the removed names. The corrected
matrix crosses entry-point mode with implementation ownership, and custom
registry/composite coverage guards against another fixed-name assumption.

The separate `StdlibRegistry.stdlibClassFqcns()` inventory used by CLI/playground
also includes source-only classes, so replacing it with registered-only names
would lose entries. Consolidating that inventory with source discovery is a
separate follow-up, not silently included in this fix.
