## 1. `.equals` between two types with no class in common: `JULC0078`

**Decision implemented (for the maintainer's review):** a Policy rejection, `JULC0078` (`EQUALS_ALWAYS_FALSE`), the code
ADR-067 D5 gave this comparison in its r4 ("reject", over "fold to `false` with a warning") and that `frontend=JAVAC` already
gives a collection operation and a type argument between unrelated types. ADR-068 r12 kept the plain `equals` a stop only
because an external validator writes it; it is one line in `EqualityRules.requireRelated`.

What each side answers, for the programs the corpus holds:

| Shape | JVM | Reference on-chain | Source |
|---|---|---|---|
| Two record classes with the same fields (`new R1(a).equals(new R2(a))`, a record and a variant of another family) | `false` | `true` (`EqualsData` of equal fields) | ADR-062 T29, #277; 11 saved `RegressionCasesTest` cases |
| `"a".equals(true)` | `false` | fails (`EqualsString` on a bool) | T34, #292 |
| `PubKeyHash.of(h).equals(h)`, `PubKeyHash.of(h).equals(ScriptHash.of(h))` | `false` | `true` (both are the bytes) | T29's erased nominal types |
| `sig.equals(redeemer)`, a `PubKeyHash` against an integer (`LoopDesugarTest`, `DialectRemovalAlternativesTest`) | `false` | fails, `UnBData: expected data` | `DialectRemovalAlternativesTest#rewritingHashEqualityWithAnIntegerStillFailsAtADifferentBuiltin` |
| `output.value().equals(redeemer)`, a `Value` against a `byte[]` | `false` | `false` here, by its representation | `DialectRemovalAlternativesTest#rewritingValueEqualityTurnsARuntimeFailureIntoAComparison` |
| `input.outRef().txId().equals(utxoRefTxId)`, a `TxId` against a `byte[]` `@Param` (external `UVerifyProxy.java:70`) | `false`, always: `TxId.equals` takes a `TxId` | `true` when the bytes match | external `julc-examples` |

Java's answer is `false` for every pair: each JuLC API type's `equals` tests its own class (`TxId`, `PubKeyHash`, the other
hash wrappers, `PlutusData`'s variants, the collections), a record's generated `equals` does too, and the subset rejects a
declared `equals` (`JULC0080`, `JULC0101`). On-chain the reference compares representations, so it answers `true`, `false` or
fails. Where Java and the chain can give different values, a compile error is safer than a value Java does not give, which
is what the brief asks for in that case. The alternative, lowering to Data equality, is the reference's behaviour, so it keeps
T29 and T34 open on the new default; lowering to the constant `false` is ADR-067's rejected option (a), which changes a
deployed script's meaning without a word.

**Who depends on it.** In the corpus, 23 programs (22 the reference accepts): the external `UVerifyProxy` (2 rows, `compile` and `compileContract`),
13 saved regression cases (T29, T34), 3 `LoopDesugarTest` and 3 `DialectRemovalAlternativesTest` programs, 1 campaign seed
and 1 `G1MustRejectTest` program the reference rejects for another reason. The external validator stops with `JULC0078` at
line 70; Java already answers `false` there, so its `mintAdmin` path never passes on the JVM, and its on-chain tests pass only
because the reference compares the bytes. Its fix is a typed comparison, `input.outRef().txId().equals(new TxId(utxoRefTxId))`, which
`JavacM5aTest#aTypedComparisonReplacesIt` compiles. The three `LoopDesugarTest` and
three `DialectRemovalAlternativesTest` programs compile on the default frontend and join M5's test rewrite (follow-ups, "Test
sources M5 must rewrite").

**Limit.** `EqualityRelation` calls two types unrelated when neither is a subtype of the other by class. Two interfaces that
are not sealed could both be implemented by one record, and Java could then answer `true`; the subset holds no such pair in
the corpus, and the rule fails closed there (a compile error), with a message that says Java keeps them distinct.

## 2. An expression javac types `Object`, `Record` or an intersection

javac types a conditional or a `switch` by its target where it is an argument of an `Object` parameter (`s.equals(c ? a : b)`),
by the least upper bound under `var` (`Record & S`), and a component read through a raw type as its erased variable
(`Tuple2 t; t.first()` is `Object`). None of these has a representation, so `Typing.of` stopped. Now, in `Typing.unrepresented`:

- a conditional or a `switch` (`Object` as an argument, `Record` between two records, `Record & S` between two variants) is
  its arms' one type; Data where the arms differ and are all Data-shaped (records, sums, Data,
  `Optional`), which is their encoding and what the reference gives a `switch` (`TypeInferenceHelper.switchResultType`); and
  otherwise `PirHelpers.UNKNOWN`, which no encoding takes (`JULC0012`), as the reference says of a `switch`;
- a record component read through a raw type is the field of the record's representation: Data for a raw `Tuple2`/`Tuple3`,
  as the reference reads it;
- a variable of such a type holds what its initializer was typed (`Typing.of(tree, lowered)` reads the binder);
- a constructor's component of `UNKNOWN` type is `JULC0012`, as the reference says of a diamond's or a raw tuple's
  component (`Records.fields`).

A first version also typed an intersection by its one bound with a representation (`Record & S` as `S`); no program, test or
mutant told it from the arms' rule, so it was removed (`9c1717aa`).

**Closed by M5 (D4's cap).** The reference types a conditional by its then branch, so `JulcList.of(c ? a : Builtins.iData(a))`
encodes the Data branch with `IData` and fails where the JVM's list holds the Data
(`Adr068M5aHarnessTest#theReferenceReadsAConditionalsElseBranchAsItsThenBranch`). `frontend=JAVAC` holds a conditional to the
`switch`'s rule and rejects it with `JULC0012` (`JavacM5aTest#armsOfDifferentRepresentationsAreNotEncoded`). No corpus row reaches it.

## 6. `JULC0084` in `src/main` that the corpus does not reach, and the plan

### The recheck tool, hardened

`Adr068BytesRecheckTest` (run by `adr068Recheck`) now:

- **draws random inputs**: 200 per case beyond the recorded inputs and the fixed samples, from a generator per parameter type
  (integers from -4 to 8, one in eight from -150 to 150; booleans; byte strings; key hashes of 28 bytes; strings; `PlutusData` of
  four shapes; lists and maps of 0 to 5 elements of any of these, a map's keys distinct; `Optional`; and a record or sealed
  interface the source declares, as the constructor of one of its records with its tag). The seed is the case key's first 60 bits,
  so a rerun draws the same inputs (two runs, `all4` and `all5`, gave the same inputs and classes on all 313 keys);
- **counts the inputs on which the JVM returns a value**, and reports it;
- **refuses Cost change and Representation only below 10 such inputs** (`ENOUGH_VALUES`), unless every input of the method's input
  space ran (no parameter, or booleans alone): that is `FEW-VALUES`, settled by hand with inputs that reach a value or with the
  reason none exists. Ten is a floor, not a proof: it means the program's value path ran on ten distinct inputs at four levels on
  both frontends, so a decoding the reference gets wrong on that path shows. A semantic difference found is a Semantic fix
  whatever the count;
- **makes a shared departure visible**: `ALIKE` when both frontends depart from the JVM the same way, never folded into Cost change
  or Representation only; and `FAILS-CLOSED` when the javac frontend's script fails where the JVM returns while the reference gives
  the JVM's answer (O7's shape), apart from `FINDING` (any `JAVAC` value other than the JVM's);
- **compares script size** with and without a source map, and a case the JVM cannot run (a validator, a pool) is compared between
  the frontends at both map settings and is never proposed as Cost change or Representation only (no JVM value was seen).
