# ADR-068 M3: the reference change B2 → B3

`a.mod(b)` with `b` below 1, and `take(n)` and `drop(n)` with `n` below 0, throw in Java, and the script returned a value. They now fail in
the script, on both frontends, which re-freezes the reference as **B3** (I1, "Reference changes"; D4, exception 2).

| Change | Commit |
|---|---|
| `TypeMethodRegistry`'s `mod`, `take` and `drop` check their argument, through `PirHelpers.failingBelow` and `failIfBelow` | `6068c83d` |

This is one reference change, and only these handlers move the reference with the gate off. `ListsLib.take` and `ListsLib.drop` take it
through the same handlers.

B2 is M3a's reference ([`068-m3a-reference-b2.md`](068-m3a-reference-b2.md)); its rows are not edited. B3's rows are new files beside them,
generated by the same tool over the same frozen corpus, with 2 new pins. Machine and toolchain as in M0's evidence.

## The check

The receiver is evaluated, then the argument, then the check, then the operation, as in Java. Each operand is bound once unless evaluating
it has no effect. `IfThenElse(argument < least, Error, operation)` takes no trace, so it adds no text to a script.

**A constant that cannot fail takes no check.** A local test on the argument term decides, with no pass: an integer `Const` at or above the
bound. `x.mod(BigInteger.TEN)`, `x.mod(BigInteger.valueOf(7))`, `x.mod(new BigInteger("7"))`, `take(3)`, `take(0)` and `drop(0)` compile to
the bytes they did. A constant below the bound keeps the check, and fails.

**How these read in the corpus.** Across 10,379 distinct sources: `mod` appears 3 times, with `BigInteger.TWO`, `BigInteger.valueOf(5)` and
`BigInteger.valueOf(b)`. `take` appears about 1,380 times and `drop` about 1,390, nearly all from one ADR-060 family, `items.take(probe.longValue() - 5)`,
compiled under many names. That is an expression, so it takes the check, and it is why 1,584 cases move. A constant is 2 of the rest.

## What Java and the script do

Each row ran on the JVM and through the frontends named, at every level, over small values on both sides of each boundary
(`Adr068ThrowingMethodsTest`, jqwik with the JVM as the model).

| Method | Java | Script, before B3 | Script now |
|---|---|---|---:|
| `a.mod(b)`, `b < 0` | Throws | **A value** | Fails |
| `a.mod(0)` | Throws | Fails | Fails |
| `take(n)`, `n < 0` | Throws | **An empty list** | Fails |
| `drop(n)`, `n < 0` | Throws | **The whole list** | Fails |
| `ListsLib.take`, `ListsLib.drop`, `n < 0` | Throws | **As above** | Fails |
| `a.divide(b)`, `a.remainder(b)`, `a / b`, `a % b`, `b = 0` | Throws | Fails | Unchanged, agrees |
| The same, any other `b`, of either sign | Truncates | Truncates | Unchanged, agrees |
| `MathLib.pow(a, b)`, `b < 0` | 1, by its own loop | 1 | Unchanged, agrees |
| `MathLib.floorDiv`, `floorMod`, a negative or zero `b` | As the method's Java | The same | Unchanged, agrees |
| `a.pow(n)`, `a.shiftLeft(n)`, `a.shiftRight(n)`, `a.modPow(e, m)` | A value, or throws | Does not compile: `JULC0055` | Unchanged |
| `list.get(i)`, `i < 0` or `i >= size` | Throws | Fails | Unchanged, agrees |
| `head()`, `tail()` on an empty list | Throws | Fails | Unchanged, agrees |
| `tail()` on an empty `JulcMap` | Throws | Fails | Unchanged, agrees |
| `Optional.get()` on an empty one | Throws | Fails | Unchanged, agrees |
| `ByteStringLib.take`, `drop`, `slice`, a negative or long `n` | Clamps | Clamps | Unchanged, agrees |
| `ByteStringLib.at`, out of range | Throws | Fails | Unchanged, agrees |
| `ByteStringLib.zeros(n)`, `n < 0` | Throws | Fails | Unchanged, agrees |

`MathLib`, `ListsLib` and `ByteStringLib` rows ran on the JavaParser frontend alone: a library unit stops on the javac frontend until
library lowering. No other neighbour accepts what Java rejects. `JulcMap.head()` on an empty map and `JulcArray.get` were read, not run: the
first's Java throws and its handler is `HeadList`, and the second's is `IndexArray`, which fails out of range.

## What this does not establish

- **Two differences stay,** as known issues, because the script accepts and rejects what Java does: argument-first `prepend`, `contains` and
  `insert`, and duplicated operands in T13's family. See the follow-ups and the release notes.
- **An on-chain run.** DevKit was not run. The harness's VM is the evidence.
- **Recorded evaluations.** Those whose script hash moved are no longer replayed against the recording, as the counts above say.
