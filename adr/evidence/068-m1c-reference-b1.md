# ADR-068 M1c: the reference change B0 → B1

The changes [ADR-068](../068-javac-frontend-migration.md) assigns to both frontends at M1, made in the JavaParser
frontend (the I1 reference) and julc-core, re-freeze the reference as **B1** (I1, "Reference changes"):

| Change | Decision | Commit |
|---|---|---|
| JuLC's JVM collections compare `byte[]` elements, keys and values by content | D6, "JuLC's JVM collections" | `38ef9a53` (with the T10 pin, `40b6beed`) |
| `a.compareTo(b) OP 0` evaluates `a`, then `b`, once each (#146); `>` and `>=` evaluate left to right (#295) | D6, D4 exception 1 | `9992b1df` |
| A `JulcArray` in a Data-encoded position is `JULC0091` (#298): where its type is written, and where lowering Data-encodes a value (review F601, F700) | D6, D4 exception 2 | `44c32b8c`, `efd1bc0c` |

B0 is the M0 reference ([`068-javac-frontend-baseline.md`](068-javac-frontend-baseline.md)); its rows are not edited.
B1's rows are new files beside them, generated by the same tool over the same frozen corpus, from the code of
`c972246e` (the base `42e7bd51` plus the three changes, the review fixes, and the ledger tool's correction of
`3425aefe`). Machine and toolchain as in M0's evidence.

    --variant "reference change (compareTo rule)"=<v146> --variant "reference change (#295 operand order)"=<v295> \

The equality scan and the accepted-divergence list are not regenerated: D4's list is frozen at M0, and nothing M1c
changes is read by the scan. Two runs each of B0 and B1 (14 compile threads, and one) give identical files, once the
ledger tool drops identity hashes from failure details (below).

## The B0 → B1 differences, classified (D13)

[`068/ledger-b0-b1-diff.tsv`](068/ledger-b0-b1-diff.tsv) lists every differing case, with its changed levels (FLAT
sizes, or rejection codes), whether its source-map digest changed, its changed runs, and its attribution (the
variant whose switch reverts it, then its D13 class). 7,316 of the 10,960 frozen cases differ:

| Rows | What differs | Cause | D13 class |
|---|---|---|---|
| 6 | bytes, semantic observations | the five `diverge-g1-146-traced-compare-operand*` pins (four programs) and the two T13 pins now agree with the JVM | Reference change (D4 exception 1); semantic fix, #146 |
| 463 | bytes, budgets (322 G0, 99 G1, 42 saved cases) | the `compareTo` rule | Reference change; cost change, every budget smaller |
| 6,845 | bytes (6,840 recorded, 2 Blaster fixtures, 3 stdlib providers) | the `compareTo` rule | Reference change; semantics not observed, equivalent modulo evaluation count (D4 exception 1); every FLAT size smaller |
| 1 | diagnostic: uncoded strict-boundary error → `JULC0091` | `List<JulcArray<BigInteger>>` redeemer (`StrictDataBoundaryTest`) | Reference change (D4 exception 2); diagnostic change, an uncoded rejection gaining a code |
| 1 | the JVM observation and verdict of `diverge-t10-map-byte-array-key` | `JulcAssocMap` finds an equal `byte[]` key | julc-core off-chain change (D6); semantic fix, JVM side |

Of the byte changes, 6,149 also change the source-map digest (the comparison's terms change: provenance follows
the bytes). Levels: 6,441 cases change at every level, 865 only at `NONE` (stdlib methods a program does not call
stay in it at `NONE`, and the stdlib compares with `compareTo(…) OP 0`), 9 at `NONE`, `PV11_SAFE` and `PV11_COSTED`.

**No size or budget grows.** Every changed FLAT size is smaller (7,311 cells at `NONE`, 6,437 at `BASELINE`, 6,446 at
`PV11_SAFE` and `PV11_COSTED`), and so is every changed CPU and memory budget (1,268–1,283 runs per level). Over the
changed runs, `PV11_SAFE` CPU falls from 32.7·10⁹ to 24.3·10⁹ and script bytes from 1,638,329 to 391,522 (the two
T13 programs were most of that size).

## Cost: `a.add(b) > c.multiply(b)` and its `compareTo` form

`static boolean m(BigInteger a, BigInteger b, BigInteger c)`, evaluated at `(5, 2, 3)` on the Java VM:

| Form | Level | B0 bytes | B0 CPU / memory | B1 bytes | B1 CPU / memory |
|---|---|---|---|---|---|
| `a.add(b) > c.multiply(b)` (dialect) | every level | 41 | 1,083,783 / 5,101 | 44 | 1,131,783 / 5,401 |
| `a.add(b).compareTo(c.multiply(b)) > 0` | `NONE`, `BASELINE` | 76 | 2,069,665 / 8,509 | 44 | 1,131,783 / 5,401 |
| | `PV11_SAFE`, `PV11_COSTED` | 68 | 1,693,567 / 7,107 | 44 | 1,131,783 / 5,401 |

On B1 the two forms compile to the same script at every level: the dialect pays the one `let` that evaluates
`a.add(b)` first (+3 bytes, +48,000 CPU, +300 memory over B0's swapped order), and the `compareTo` form costs exactly
that order-correct lowering, which is M1's rewrite gate (D4). Three such comparisons joined by `&&` (`>`, `<`, `>=`):
dialect 80/72 bytes (`NONE`/`PV11_SAFE`) at B0 and 85/77 at B1; the `compareTo` form 183/151 at B0 and 85/77 at B1.
