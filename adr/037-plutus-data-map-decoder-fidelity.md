# ADR-037: Preserve Plutus Data map associations during byte decoding

## Status

Implemented and validated; implementer review complete. Independent review pending before merge.

## Context and current behavior

Issue #54 fixed map encoding but explicitly deferred byte decoding. The #55 audit
confirmed Scalus 1.1.0 preserves map associations; it also reproduced a separate
core defect: decoding `a2010a0114` yields `{1:20}` instead of `{1:10,1:20}`.
`PlutusDataCborDecoder.decode` first constructs a cbor-java 0.9 tree. Its `Map`
uses key equality and overwrites duplicates before `fromDataItem` sees them.
FLAT Data constants use this same byte decoder, so program read-back changes
literal values. In-memory encoder `OrderedMap` conversion already preserves them.

## Goals and non-goals

Preserve the ordered association sequence, recursively, for definite and indefinite
maps. Keep existing non-map decoding, constructor Word64 handling, byte encoding,
compiler lowering, public signatures and VM selection unchanged.

This is not a replacement CBOR parser, ledger acceptance certification, canonical
byte preservation for noncanonical encodings, or global decoder resource-hardening
project. The existing decoder has no explicit CBOR depth/total-size limit; this
change must not claim otherwise. It cannot recover entries already lost by an
external cbor-java `Map`.

## Invariants

- Every decoded map entry appears exactly once in input order, even for equal,
  compound, differently encoded equal, or duplicate-containing map keys.
- No key equality, hash or sorting operation determines the authoritative entries.
- Definite maps read exactly the declared number of complete key/value pairs.
- Indefinite maps end only at a break in key position; EOF, missing values and
  breaks in definite-map entry/value positions fail with `CborDecodingException`.
- Declared map lengths cannot drive unbounded preallocation or overflow into an
  indefinite-length interpretation. Each pair needs at least two remaining bytes.
- Valid non-map data and duplicate-free maps retain their decoded values. Encoder
  output and compiler-generated bytes are unchanged. Canonically encoded programs
  containing duplicate Data map keys now retain their bytes on read/re-encode.

## Decision and design review

Use a package-private cbor-java decoder subclass that peeks at the next header in
its owned `ByteArrayInputStream`. Intercept only major type MAP; delegate all other
items to the original decoder. cbor-java array and tag decoding call the virtual
`decodeNext`, so nested maps are intercepted too. Its default decoding options
remain unchanged. Reuse the existing `OrderedMap` and `fromDataItem` conversion;
the compatibility hash-map view is not authoritative.

Reuse cbor-java's unsigned `getLengthAsBigInteger` header parsing. Bound definite
map counts by remaining input bytes before converting to int. Accumulate actual
entries without preallocating from untrusted counts. Reject misplaced breaks and
incomplete pairs explicitly. This deliberately rejects malformed map forms that
the old conversion sometimes silently skipped; it does not introduce a general
strict-CBOR mode. Preserve existing top-level sequence handling (parse the complete
sequence, return its first item), unknown-tag behavior and non-map permissiveness.

## Alternatives

- Reject duplicates: violates Plutus Data association-list semantics.
- Change only `fromDataItem`: too late; duplicate entries are already overwritten.
- Replace the entire parser: needlessly expands semantic and malformed-input risk.
- Copy/patch cbor-java or use reflection to replace its map decoder: adds dependency
  maintenance or private-implementation coupling; public virtual dispatch suffices.
- Introduce another map tree: unnecessary; reuse the encoder's lossless map model.

## Affected stages/modules and compatibility

Production changes are confined to `julc-core` CBOR byte parsing; all callers,
including FLAT program decoding, benefit. Core regression tests and benchmark
cross-VM tests exercise the change. No lowering, encoding, ledger representation,
public API signature, dependency or cost-model change. Existing stored bytes and
on-chain scripts are untouched. Re-encoding a previously misdecoded duplicate-key
script can now differ from the old, lossy result; that is the intended correction.

## Risks and verification strategy

Verify virtual recursion under arrays/tags and maps in key/value positions. Test
unsigned lengths, truncation, odd indefinite maps, reserved headers and misplaced
breaks. Fixed CBOR fixtures give an independent oracle; generated recursive data
provides composition coverage. Differential checks against the old parser pin
non-map and duplicate-free compatibility. Check canonical FLAT byte stability and
actual `serialiseData`/Data equality behavior on Java, Truffle and Scalus (language
compatibility only, not Scalus ledger certification). Run core, downstream suites
and full build. Existing depth/resource limitations remain deferred.
