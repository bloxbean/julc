JuLC Compiler Troubleshooting Guide

This guide maps every compiler, validation, configuration, and runtime error to its cause and solution. All error messages shown here are taken directly from the JuLC source code.

1. Compilation Errors (lowering)

Section titled “1. Compilation Errors (lowering)”

These errors are emitted during PIR (Plutus Intermediate Representation) generation, when the compiler translates Java AST nodes into UPLC-compatible terms.

Conditional update to loop-body local '<name>' is not supported

Section titled “Conditional update to loop-body local '<name>' is not supported”

An if/else inside a loop updates a local declared in the loop body outside that branch. The branch carries only loop accumulators out; the old lowering silently lost this local’s update. Even constant conditions and unused updates are rejected.

Alternatively, declare the variable before the loop as an accumulator (reset it each iteration when needed), or declare it inside the branch if its value is only used there. Existing break-aware and native-accumulator restrictions still apply; see the full rules.

Switch-expression arm cannot update enclosing variable '<name>'

Section titled “Switch-expression arm cannot update enclosing variable '<name>'”

A switch exports only its yielded result, not assignments to enclosing variables. A nested loop inside an arm does not change this rule. It applies to outer accumulators as well as loop-body locals, with or without an enclosing if.

Do not declare local outside the arm and expect the loop to update it there. Loops inside an if at method level or in a switch arm now preserve their accumulator updates after the branch (#161). If using an older compiler affected by this bug, upgrade and recompile; script hashes and budgets may change. This includes a switch expression inside an outer loop body: declare the accumulator inside the arm, update it with the guarded loop, and yield its result. Older versions may conservatively reject this composition as a conditional loop-body local update. Updates to variables declared outside the arm, or to actual loop-body locals across an if, remain rejected.

Reassignment of switch case-pattern variable '<name>' is not supported

Section titled “Reassignment of switch case-pattern variable '<name>' is not supported”

Updating a case-pattern binding could leave field projections pointing at its original record (#162). Reassignment is now rejected, including when only the record is yielded. Copy the binding to a fresh arm-local accumulator:

1.1 JULC0001 Method must have a body: <name>

Section titled “1.1 JULC0001 Method must have a body: <name>”

Cause: A method the program calls has no body, such as a native method. The compiler lowers every method a validator calls, so each one needs a body.

Fix: Give the method a body. An abstract method that nothing calls is never lowered.

1.2 Variable must be initialized: <name>

Section titled “1.2 Variable must be initialized: <name>”

Full message: Variable must be initialized: <name>. Hint: On-chain variables need initial values, e.g. var <name> = BigInteger.ZERO;

Cause: A local variable was declared without an initializer. On-chain code requires all variables to be initialized at declaration because UPLC has no concept of uninitialized memory.

Fix: Always assign an initial value.

1.3 break statement outside of a loop

Section titled “1.3 break statement outside of a loop”

Full message: break statement outside of a loop Hint: break can only be used inside for-each or while loops.

Cause: A break statement appeared outside of a for-each or while loop scope. A break inside a loop that updates no variable declared before it reports JULC0063 instead (1.25). A break that names a label reports JULC0066 (1.29).

Fix: Move the break inside a loop body, or restructure your logic to use return instead.

1.4 Unsupported statement: <StatementType>

Section titled “1.4 Unsupported statement: <StatementType>”

Section titled “1.28 JULC0060 continue is not supported on-chain”

Cause: continue is outside the on-chain subset. Loops are compiled to folds and recursive functions whose body runs to its end on every iteration; there is no lowering that skips the rest of the body. Before #257 this was reported as Unsupported statement: ContinueStmt, without a code.

Cause: Labelled statements are outside the on-chain subset, so no break or continue can name a label. 2.16 JULC0056 Assignment to field '<field>' in a loop is not supported

Section titled “2.16 JULC0056 Assignment to field '<field>' in a loop is not supported”

Cause: A loop updates a static field or @Param. On-chain fields are not shared state: the update rebinds the name only in the rest of the method’s current run. Every other method, and every other run of the same method, sees the field’s initial value. The update is accepted only where that gives Java’s result, and the message says which condition failed:

  • the field is final
  • '<method>' is not an entry method: only a validator entrypoint, a multi-validator handler or the compileMethod target may update a field. A helper or a library method can be called more than once.
  • '<method>' calls itself or '<caller>' calls '<method>': the entry method would run more than once.
  • the loop is in a lambda: the lambda can run more than once.
  • a static field initializer cannot update a field
  • '<method>' reads it: another method would see the initial value. A method whose local, parameter or lambda variable has the field’s name does not read the field.

Fix: Copy the field into a local accumulator before the loop, update the local, and pass it to the methods that need it.

2.17 JULC0058 Reassigning loop variable '<name>' is not supported in a loop that updates no variable declared before the loop

Section titled “2.17 JULC0058 Reassigning loop variable '<name>' is not supported in a loop that updates no variable declared before the loop”

Cause: A for-each loop reassigns its loop variable, or a local declared in its body, and updates no variable declared before the loop. Such a loop compiles its body as plain statements, which cannot reassign a variable. A loop that also updates an earlier variable (an accumulator) can reassign its loop variable and body locals. The message says local variable for a body local.

Fix: Declare a new local for the new value instead of reassigning.

2.18 JULC0059 Pattern variable '<name>' has the same name as a field of <Class>

Section titled “2.18 JULC0059 Pattern variable '<name>' has the same name as a field of <Class>”

Cause: An instanceof pattern variable has the same name as a field of the class, including a @Param field. The rule dates from JuLC’s first frontend, which resolved names by spelling, so such a name could read or update the field instead of the variable. The name is rejected in every position.

Fix: Rename the pattern variable. switch case patterns are not affected.

2.19 JULC0070 Integer literal <literal> is invalid: <reason>

Section titled “2.19 JULC0070 Integer literal <literal> is invalid: <reason>”

Cause: javac rejects the literal, and so does JuLC (#270) (JLS 21 §3.10.1):

  • An int literal has 32 bits and a long literal (suffix L) 64. A decimal literal must fit the signed range; 2147483648 and 9223372036854775808L are allowed only directly after a unary minus, not inside parentheses. A hexadecimal, octal or binary literal must fit the width.
  • An octal literal (a leading 0) has only the digits 0 to 7, so 08 is invalid.
  • A byte[] initializer element must be in -128 to 127.

A hexadecimal, octal or binary literal that fits denotes the two’s-complement value of its bits, as in Java: 0xFFFFFFFF is -1, and 0xFFFFFFFFL is 4294967295.

Fix: Add the L suffix for a long literal, use BigInteger for a larger value, write a negated most-negative literal without parentheses, and keep byte[] elements in range.

JULC0095 <field or block> is not lowered, so ...

Section titled “JULC0095 <field or block> is not lowered, so ...”

Nothing lowers any other field (a @Param, an instance field, a field of a nested type or a record), and nothing lowers an initializer block. A library’s static field binds at script start, whether or not Java initializes the class, so it counts as one of these.

Fix: Such a field holds only a literal, a new byte[]{...} of literals, BigInteger.ZERO, ONE, TWO or TEN, PlutusData.UNIT, a constant variable, or Boolean.valueOf(true) or Boolean.valueOf(false). Move anything else to a static field of the class being compiled, or to a method. Keep an initializer block empty.

JULC0101 <method or component> has a name JuLC reads in place of its body, so a program does not declare it

Section titled “JULC0102 These string constants are joined when the script runs”

A warning; the program still compiles. Java joins string constants when it compiles, and JuLC keeps a + as written, so the script joins them each time it runs.

Section titled “JULC0103 Entrypoint <method> of <class> takes <type> as its last parameter; the last parameter is the script context, ScriptContext or PlutusData”

Cause: An @Entrypoint method of a validator declares its last parameter with a type other than org.julclang.ledger.ScriptContext or org.julclang.core.PlutusData. The script receives the script context there, undecoded, so a parameter typed BigInteger, a record or a subtype of PlutusData reads the context as that type, and the method’s JVM test does not test the script. A type of your own named ScriptContext is not the ledger’s. An entry point with a parameter count its purpose does not take is JULC0008 instead.

Section titled “JULC0080 Record <record> declares <member>, which JuLC does not compile; a record body may contain only nested type declarations”

JuLC compiles a record as its components only, so such a member is never what the script runs. A declared accessor or toPlutusData is JULC0101, and a constructor with a statement JULC0099.

JULC0087 <operation> compares <type>, whose equality on the JVM compares an array by identity

Section titled “JULC0087 <operation> compares <type>, whose equality on the JVM compares an array by identity”

Cause: an equals, or a collection operation that compares elements or keys (contains, get, lookup, containsKey, delete), at a type whose JVM equality compares a byte[] by reference: byte[].equals, a record or sealed variant with a byte[] component, or an Optional, tuple or java.util collection of one. Section titled “JULC0086 <expression> compares <type> by reference; use equals”

Cause: == or != between references (BigInteger, byte[], String, boxed values, records) is reference equality in Java and value equality on-chain. Constant strings built from literals and + alone keep their meaning.

JULC0113 Conditional update to loop-body local '<local>' is not supported

Section titled “JULC0113 Conditional update to loop-body local '<local>' is not supported”

Cause: an if/else branch in a loop carries only the loop’s accumulators out of the branch, so an update of a local declared in the loop body would be lost.

Use a conditional initializer (condition ? value : otherValue), or declare the variable before the loop so it is an accumulator (reset it each iteration if needed), or declare it inside the branch if its value is only needed there.

JULC0114 Assignment to <variable> is not supported at this position

Cause: Inside a loop, an assignment is lowered only as a statement directly in the loop body or in an if/else branch of it.

JULC0116 Assignment to undeclared variable '<variable>'

Cause: an arm of a switch reads a pattern variable through projections of the matched record, so an assignment to it would not be seen.

JULC0123 Static call <call> names its class by a qualified name; on-chain code calls a static method through its class's simple name

Section titled “JULC0123 Static call <call> names its class by a qualified name; on-chain code calls a static method through its class's simple name”

Cause: JuLC resolves a static call through the simple name of its class, as an import or the enclosing class declares it, so a call through a package-qualified class name, such as java.math.BigInteger.valueOf(1), is not resolved. A nested class’s qualified name, Outer.Inner.f(a), is JULC0011.

JULC0124 Unsupported primitive type: <type>. Supported types: boolean, int, long

Section titled “JULC0124 Unsupported primitive type: <type>. Supported types: boolean, int, long”

Cause: byte, short, char, float and double have no on-chain representation, as a variable’s, a component’s or a cast’s type. The one exception is a cast of an integer literal to byte, short or char, perhaps negated, which is its Java value. A char literal elsewhere is JULC0125.

Fix: Use int or long for a number, BigInteger for an unbounded integer, boolean for a flag, and String or byte[] for text and bytes.

JULC0125 Unsupported expression: <expression>

Section titled “JULC0125 Unsupported expression: <expression>”

Cause: an expression form JuLC does not compile on-chain, such as a class literal, a text block, a char literal or a function that is not a lambda written at the call.

Fix: Write the value with a supported form: a string literal for a text block, a lambda at the call for a function, and no class literal outside PlutusData.cast.

JULC0126 <pattern> tests a value of type <type>, which is not <interface> or a variant of it; on-chain the test reads a constructor tag, which another type can share

Section titled “JULC0126 <pattern> tests a value of type <type>, which is not <interface> or a variant of it; on-chain the test reads a constructor tag, which another type can share”

Cause: an instanceof pattern on a variant reads the value’s constructor tag. That answers Java’s question only when the value’s static type is the variant’s sealed interface or the variant itself: a value of another type, through a widening cast to Object for one, can carry the same tag.

Fix: Test a value of the sealed interface’s type, or switch over it.

JULC0127 <variant> is a variant of <interface> that is not a plain record; a variant is a record, not a class or a @NewType, so that it has one constructor tag and its fields

Section titled “JULC0127 <variant> is a variant of <interface> that is not a plain record; a variant is a record, not a class or a @NewType, so that it has one constructor tag and its fields”

Cause: JuLC encodes a sealed interface’s value as a constructor whose tag is the variant’s place among the permitted records, and whose fields are the record’s components. A final class or a @NewType has neither. It is reported at a new, an instanceof or a case of such a variant, and otherwise at the variant’s declaration wherever its sealed interface is declared in a unit the compilation reads, whether or not the program uses the sum: such a sum has no layout, so a value of it would be dropped wherever the sum is read.

Fix: Make the variant a record that is not a @NewType.

JULC0128 <operation>: <reason>

Section titled “JULC0128 <operation>: <reason>”

Cause: the value’s on-chain representation is not the one this operation takes, and no conversion keeps Java’s value: Data where a builtin takes bytes, a native list where a component holds Data, a ledger type that holds a map, whose Data repeats a key the JVM’s map holds once.

Fix: Convert explicitly: Builtins.unBData for bytes, Builtins.listData or Builtins.mapData for a list or a map, or read the map through the stdlib’s ValuesLib and MapLib.

JULC0129 Cannot construct non-record type: <type>

Section titled “JULC0129 Cannot construct non-record type: <type>”

Cause: a new of a class that is not a record, a tuple, a sealed variant or a supported API type. On-chain a value is a record’s components, and a class’s constructor and fields have no on-chain form.

Fix: Only record types can be constructed on-chain. Declare the type as a record.

JULC0130 Compound assignment <op> to the int '<name>' takes a long

Section titled “JULC0130 Compound assignment <op> to the int '<name>' takes a long”

Cause: Java’s int x; x += someLong; casts the result back to int without saying so. An on-chain integer has no width, so past 32 bits a JVM test and the script would give different values. A Long javac inferred counts too, as in for (var z : JulcList.of(y)) { x += z; }: Java unboxes it first.

Fix: Declare the variable as long, which is what most code means: long total = 0; total += amount;. Use BigInteger for values that can pass 64 bits. If you do want Java’s 32-bit result, write the cast: x = (int) (x + y);.

Fix: Store a JulcList, and build the array where it is used.

4.12 JULC0092 Sealed interface '<name>' has no permits clause, and its permitted subclasses (<types>) are not exactly the records nested in it

Section titled “4.12 JULC0092 Sealed interface '<name>' has no permits clause, and its permitted subclasses (<types>) are not exactly the records nested in it”

Cause: A variant’s Data tag is its position in the permits clause. Without one, JuLC uses the order of the records nested in the interface. Java also permits other classes of the same file implicitly, such as top-level records, and those have no tag under that rule.

Fix: Add a permits clause listing every variant, in tag order.

4.13 JULC0093 A string literal holds the unpaired surrogate U+<hex>, which a UPLC string cannot hold

Section titled “4.13 JULC0093 A string literal holds the unpaired surrogate U+<hex>, which a UPLC string cannot hold”

Cause: javac accepts a lone UTF-16 surrogate in a string literal, but a UPLC string is Unicode text, so the script would hold a different string from the Java program.

Fix: Write a supplementary character as its high surrogate followed by its low surrogate, or remove it.

4.14 JULC0131 PlutusData.cast() needs a class literal as its second argument

Section titled “4.14 JULC0131 PlutusData.cast() needs a class literal as its second argument”

Cause: The target type of PlutusData.cast must be known when the script is compiled, so the second argument must be a class literal written directly, not wrapped in parentheses or computed.

Fix: Write the class literal directly.

5. Runtime Errors

Section titled “5. Runtime Errors”

These errors occur when evaluating compiled UPLC programs on the Plutus VM.

5.1 No JulcVmProvider found. Add julc-vm-scalus or julc-vm-java to your classpath.

Section titled “5.1 No JulcVmProvider found. Add julc-vm-scalus or julc-vm-java to your classpath.”

Cause: The JulcVm.create() method could not find any VM provider via ServiceLoader. No VM backend JAR is on the classpath.

Fix: Add a VM backend dependency to your project.

5.2 EvalResult.Failure

Section titled “5.2 EvalResult.Failure”

Cause: The UPLC program evaluated to an error term. This typically means the validator returned false or hit a Builtins.error() call. The error field contains a description of the failure.

Fix: Check the trace messages via result.traces() for debugging output. Ensure your validator logic returns true for valid transactions. Add ContextsLib.trace("message") calls to narrow down the failure point.

5.3 EvalResult.BudgetExhausted

Section titled “5.3 EvalResult.BudgetExhausted”

Cause: The UPLC program exceeded the allowed execution budget (CPU steps and/or memory units). This happens when the script is too expensive.

Fix:

  • Simplify your validator logic
  • Reduce the number of loop iterations
  • Use break in for-each loops to exit early
  • Avoid deeply nested data structure traversals
  • Check result.budgetConsumed() to understand where the budget went
  • Consider splitting logic across multiple transactions

5.4 Script too large for on-chain submission

Section titled “5.4 Script too large for on-chain submission”

Cause: The compiled UPLC program serialized to CBOR exceeds the protocol parameter maxTxSize (currently ~16 KB for the script itself). This is not a compiler error but a chain-level constraint.

Fix:

  • Remove unused helper methods (they are included in the script)
  • Use stdlib methods from julc-stdlib (compiled once, shared via reference)
  • Simplify logic, reduce the number of record types and sealed interfaces
  • Use @Param fields to move configuration data off-chain (applied at deployment)

6. Common Mistakes

Section titled “6. Common Mistakes”

Q: Why does my validator always return false?

Section titled “Q: Why does my validator always return false?”

A: It is not a missing return: a method that can end without one does not compile. javac reports JULC0085 missing return statement (compiler.err.missing.ret.stmt).

A validator that compiles and rejects every transaction usually checks something the transaction does not hold: a signer missing from signatories(), an output paid to another address, or a datum or redeemer whose fields are in a different order from the record. Trace each check (see How do I debug a failing validator?) to find the one that fails, and build the test’s script context with exactly the values that check reads.

Q: Why do I get “Undefined variable” for a variable I just declared?

Section titled “Q: Why do I get “Undefined variable” for a variable I just declared?”

A: Variables are scoped to the block they are declared in. If you declare a variable inside an if block, it is not visible outside.

Q: Why can I not reassign a variable?

Section titled “Q: Why can I not reassign a variable?”

A: On-chain variables are immutable. Reassignment is only supported inside for-each and while loops as the accumulator pattern. Outside of loops, create a new variable with a different name.

Q: Why does BigInteger.valueOf(42) not work?

Section titled “Q: Why does BigInteger.valueOf(42) not work?”

A: BigInteger.valueOf(n) is actually supported by the compiler. It translates the argument directly to a UPLC integer. If you see an error, check that the argument is a literal, not a variable.

Q: How do I use List.of(...) on-chain?

Section titled “Q: How do I use List.of(...) on-chain?”

A: List.of() is not directly supported. Use Builtins.mkNilData() to create an empty list and Builtins.mkCons() to prepend elements.

Q: Why does my library class get “Unknown method” errors?

Section titled “Q: Why does my library class get “Unknown method” errors?”

A: Library methods must be called with their class name qualifier.

If the library is a separate file, ensure it is annotated with @OnchainLibrary so it can be auto-discovered from the classpath via META-INF/plutus-sources/.

Q: How do I debug a failing validator?

Section titled “Q: How do I debug a failing validator?”

A: Use ContextsLib.trace() to emit messages during evaluation. Trace messages are collected in EvalResult.traces().

Q: Why do I get “Circular type dependency detected”?

Section titled “Q: Why do I get “Circular type dependency detected”?”

A: Records that reference each other cannot be topologically sorted. Break the cycle by using PlutusData as an intermediate opaque type.

Q: Why does my switch expression fail with a compiler error about missing cases?

Section titled “Q: Why does my switch expression fail with a compiler error about missing cases?”

A: The compiler enforces exhaustiveness for switch expressions on sealed interfaces. The default -> branch acts as a catch-all for any uncovered variants — its body is compiled and used for all variants not explicitly listed. However, for clarity and safety, prefer explicit cases for ALL variants rather than relying on default.

If you omit both a default branch and an explicit case, the compiler emits an error listing the missing variants.

Q: Why does pk.hash().hash() crash with a DeserializationError?

Section titled “Q: Why does pk.hash().hash() crash with a DeserializationError?”

A: Types like PubKeyHash, TxId, ScriptHash, and DatumHash map to ByteStringType. The field access pk.hash() already generates UnBData(HeadList(...)) to extract the raw ByteString. Calling .hash() again applies a second UnBData on the already-unwrapped ByteString, causing UnBData(ByteString) to fail.

Section titled “Q: Why can’t I access typed elements from a list.map(...) result?”

A: The map HOF wraps each lambda result to Data, so the returned list is JulcList<PlutusData> regardless of input element type. Use Builtins.unIData() or Builtins.unBData() to extract the typed value:

Q: Can I call foldl as an instance method on a list?

Section titled “Q: Can I call foldl as an instance method on a list?”

A: No. foldl is not registered as an instance method because it takes two lambda parameters plus an initial value, which makes instance-call syntax ambiguous. The intrinsic ListsLib.foldl has no Java declaration, so javac rejects it. Write a fold as an accumulator loop.

Q: Why does Value.assetOf(policyId, tokenName) fail?

Section titled “Q: Why does Value.assetOf(policyId, tokenName) fail?”

A: Value.assetOf() uses EqualsData internally. If policyId/tokenName are byte[] (ByteStringType), you must wrap with Builtins.bData() before passing. Otherwise EqualsData(BData(...), ByteString(...)) fails.

Q: Why does my cross-library call with BytesData variables fail?

Section titled “Q: Why does my cross-library call with BytesData variables fail?”

A: When calling a stdlib library method that takes BytesData/MapData typed parameters, if the caller also has a variable of the same type, the compiler sees matching types and skips conversion. But compiled libraries expect raw Data args at the UPLC boundary.

Q: Why does @Param PlutusData.BytesData cause issues?

Section titled “Q: Why does @Param PlutusData.BytesData cause issues?”

A: @Param values are ALWAYS raw Data at runtime, regardless of the declared type. Using PlutusData.BytesData tells the compiler the value is already a ByteString, causing double-wrapping and incorrect cross-library calls.

Q: Duplicate purpose in @MultiValidator

Section titled “Q: Duplicate purpose in @MultiValidator”

A: Two @Entrypoint methods in a @MultiValidator class have the same Purpose value. Each purpose can only have one handler. The error is JULC0138: Duplicate purpose MINT in @MultiValidator BadValidator.

Q: Cannot mix DEFAULT and explicit purposes in @MultiValidator

Section titled “Q: Cannot mix DEFAULT and explicit purposes in @MultiValidator”

A: You are combining Purpose.DEFAULT (manual dispatch) with explicit purposes like Purpose.MINT (auto-dispatch). Choose one mode. The error is JULC0136: @MultiValidator BadValidator mixes DEFAULT and explicit purposes. Two @Entrypoint methods that both use DEFAULT are JULC0137: @MultiValidator BadValidator has multiple @Entrypoint methods with DEFAULT purpose; keep one, or give each an explicit purpose.

Q: Multiple validator annotations on the same class

Section titled “Q: Multiple validator annotations on the same class”

A: A class cannot have both @MultiValidator and a single-purpose annotation (like @SpendingValidator). Use one or the other. The error is JULC0135: Class BadValidator has multiple validator annotations: @SpendingValidator, @MultiValidator.

Q: Invalid parameter count for multi-validator entrypoint

Section titled “Q: Invalid parameter count for multi-validator entrypoint”

A: In a @MultiValidator, SPEND entrypoints accept 2 or 3 parameters. All other purposes accept exactly 2 parameters.

Q: Why does my validator fail at a cast to a variant?

Section titled “Q: Why does my validator fail at a cast to a variant?”

A cast from a sealed interface to one of its record variants, such as (ScriptInfo.MintingScript) ctx.scriptInfo() or (Withdraw) redeemer, tests the variant on-chain and fails the script on any other, as Java throws ClassCastException (#288). Before this check the cast read the other variant’s fields and carried on. If the value can legitimately be another variant, branch instead:

A cast from a type JuLC cannot relate to the sealed interface remains an unchecked view, as before: (V)(Object) x, PlutusData.cast(x, V.class), casts to PlutusData’s own variants, and an operand of an unbounded type variable or an open super-interface.

Q: Why do my Java tests fail with VerifyError: Inconsistent stackmap frames?

Section titled “Q: Why do my Java tests fail with VerifyError: Inconsistent stackmap frames?”

This is a known javac bug, not a JuLC one: javac in JDK 21 to 25.0.2 can emit a class the JVM refuses to load. JDK 25.0.3 and later compile it correctly. It is triggered when a method has:

  • an if whose condition declares two pattern variables, through ||, && or ?:, for example if (p instanceof C c || p instanceof B b), and
  • later, a pattern switch whose arm copies its case variable into a local and loops over an if (p instanceof ...).

JuLC compiles such a method correctly for the chain, but your Java unit tests of it fail to load. Use JDK 25.0.3 or later to run your tests, or avoid the shape:

  • declare one pattern variable per condition, nesting a second if instead of ||/&&, or
  • move the switch into a helper method of its own.
